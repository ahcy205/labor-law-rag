# labor-law-rag 설계

- 작성일: 2026-11-17
- 상태: 승인 (2026-11-17)
- 기간: 약 4주

## 1. 무엇을, 왜 만드는가

한국 근로 제도(연차 · 퇴직금 · 주휴수당 · 최저임금 · 육아휴직 등)에 대한 질문에 **공개 문서를 근거로 출처를 달아 답하는 RAG 시스템**을 만든다. 그리고 그 품질을 **평가 세트로 재고, 실험으로 개선한 과정**을 보고서로 남긴다.

**왜:** AI 엔지니어 지원용 포트폴리오다. 앞선 프로젝트(FollowUp Agent)는 LLM Agent 설계 · 외부 연동 · 안전 설계를 보여준다. 이번 프로젝트는 그 프로젝트가 보여주지 못한 것을 채운다.

- 성능을 **숫자로** 말할 수 있다. 예: "recall@5를 0.61 → 0.84로, 환각 비율을 18% → 6%로"
- 개선이 **실험의 결과**다. 무엇을 바꿨고, 왜 바꿨고, 얼마나 좋아졌는지가 표로 남는다.
- 한국어 검색의 실제 어려움(조사 · 어미, 조문 간 참조, 조건 분기)을 다룬다. 흔한 영어 "PDF 챗봇"과 차별된다.

**주제를 근로 제도로 고른 이유:** 사용자에게 특정 전문 분야가 없어서, 전문 지식 없이도 맞고 틀림을 가릴 수 있는 분야를 골랐다. 답이 문서에 명시돼 있고 "조건 → 숫자" 구조라 검수가 쉽다. 면접관도 질문을 바로 이해한다.

**성공의 모습:** 면접관이 README를 2분 읽고 다음을 알 수 있다.
1. 어떤 문제를 풀었는가
2. 어떻게 평가했는가
3. 무엇을 시도해서 얼마나 좋아졌는가 (실험 표와 그래프)
4. 무엇이 안 됐고 왜인가

데모 화면에서 질문하면 답과 근거 조문이 같이 나온다.

## 2. 목표 · 비목표 · 반목표

### 목표
1. 공개 문서로 말뭉치를 만든다. 기준일을 정해 고정한다.
2. 평가 세트(약 150문항)를 만든다. 사람이 검수한다.
3. 기준선 RAG를 만들고, 검색 · 답변 품질을 측정한다.
4. 검색 개선 실험을 하고, 각 실험의 효과를 수치로 비교한다.
5. 이 분야 데이터로 한국어 임베딩 모델을 파인튜닝하고, 범용 모델과 비교한다.
6. 답변 생성 모델을 비교한다. 로컬 모델끼리 비교한다(8절).
7. 간단한 데모 화면을 만든다.
8. 실험 보고서 README를 쓴다.

### 비목표 (하지 않는다)
- 사용자 계정, 대화 기록 저장, 운영 수준 배포 · 모니터링
- 화려한 프론트엔드. 데모는 Gradio 수준이면 된다.
- 노동법 전 분야. 범위는 3절에 정한 법령과 주제로 한정한다.
- LangChain · LlamaIndex 같은 프레임워크 비교. 검색 단계를 직접 구성해서 원리를 보여주는 것이 목적이다.

### 반목표 (기술적으로 돌아가도 이러면 실패다)
- **평가 누수:** 테스트 문항이나 그와 거의 같은 문장이 파인튜닝 데이터나 프롬프트 예시에 들어가서 수치가 부풀려진다.
- **테스트 세트로 튜닝:** 테스트 세트 점수를 보며 설정을 고른다. 튜닝은 개발 세트로만 한다.
- **근거 없는 단정:** 검색된 문서에 없는 내용을 법률 자문처럼 단정해서 답한다.
- **재현 불가:** 보고서의 숫자를 다시 돌려서 얻을 수 없다.
- **좋은 숫자만 보고:** 효과가 없거나 나빠진 실험을 빼고 보고한다. 실패한 실험도 보고서에 남긴다.

### 3.2 범위

**법령:**
- 근로기준법 · 시행령
- 근로자퇴직급여 보장법 · 시행령
- 최저임금법, 기준일에 적용되는 **최저임금 고시**
- 남녀고용평등과 일 · 가정 양립 지원에 관한 법률
- 고용보험법 중 **육아휴직 급여 · 출산전후휴가 급여** 관련 조문과 그 조문이 위임한 시행령 조문

최저임금 고시와 고용보험법 일부는 사용자가 범위에 넣기로 했다. 사람들이 가장 많이 묻는 "올해 최저임금 얼마?", "육아휴직 급여 얼마?"의 근거가 여기에 있기 때문이다. 시행규칙과 그 밖의 고시는 넣지 않는다.

**주제:** 근로계약 · 임금 · 주휴수당 · 근로시간 · 휴게 · 연장근로 · 연차휴가 · 해고 · 퇴직금 · 최저임금 · 육아휴직 · 출산휴가

법령해석과 FAQ도 위 주제에 해당하는 것만 쓴다.

### 3.3 기준일과 법 개정

- 말뭉치는 **기준일 하나로 고정**한다(예: 수집일). 기준일 시점에 시행 중인 법령 본문을 쓴다. 보고서와 데모에 기준일을 표시한다.
- 법령해석과 FAQ는 과거 법 기준으로 쓰인 것이 있다. 작성 · 회신 일자를 메타데이터로 남긴다.
- 개정 때문에 답이 달라진 사례는 평가 세트에 **"개정" 유형**으로 넣는다. 시스템이 최신 기준으로 답하는지 본다.
- *(Claude 판단)* 법령은 기준일에 **시행 중인 조문만** 넣는다. 공포됐지만 아직 시행되지 않은 개정은 넣지 않고, 보고서 한계 절에 적는다.
- *(Claude 판단)* 옛 법 기준으로 쓰인 법령해석 · FAQ는 빼지 않고 날짜 메타데이터와 함께 둔다. 실제 자료에는 옛 문서가 섞여 있고, 그걸 다루는 것도 실험 대상이기 때문이다.
- *(Claude 판단)* 개정 유형의 정답 기준은 다음과 같다.
  - 기준일 시행 조문으로 답하고, 그 조문을 인용해야 맞다.
  - 옛 문서를 인용할 때는 작성 시점을 함께 밝혀야 한다.
  - 옛 기준의 숫자로 답하면 틀린 것으로 본다.

### 3.4 원본 보존

- 수집한 원본은 가공 전 상태 그대로 `data/raw/`에 저장한다. 수집 일시와 출처 URL을 같이 남긴다.
- 원본 데이터를 git에 올릴지는 크기와 이용 조건을 보고 정한다. 올리지 않는 경우에도, 수집 스크립트로 같은 기준일 데이터를 다시 만들 수 있게 한다.

## 4. 평가 세트

평가 세트가 이 프로젝트의 중심이다. 모든 실험은 이 세트로 비교한다.

### 4.1 문항 구성 (약 150문항)

| 유형 | 예시 | 보는 것 | 비율(대략) |
|---|---|---|---|
| 단순 사실 | "주휴수당은 주 몇 시간 이상 일해야 받나요?" | 기본 검색 | 30% |
| 조건 분기 | "입사 8개월인데 연차가 몇 개예요?" | 조건에 맞는 조항을 찾는가 | 20% |
| 문서 간 연결 | FAQ 답이 조문을 참조하는 경우 | 여러 문서를 모으는가 | 15% |
| 계산 | "월급 250만 원, 3년 근무, 퇴직금은?" | 근거 + 계산 | 10% |
| 답 없음 | 말뭉치에 근거가 없는 질문 | 모르면 모른다고 하는가 | 15% |
| 개정 | 개정 전후로 답이 다른 질문 | 최신 기준으로 답하는가 | 10% |

비율은 데이터를 보고 조정해도 된다. 조정하면 이유를 기록한다.

### 4.2 문항 하나에 담을 것

- 질문
- 정답 (짧은 정답 문장, 숫자가 있으면 숫자를 따로)
- 근거 문서 ID 목록 (검색 평가용 정답)
- 유형
- 출처 (직접 작성 / LLM 초안 후 검수 / 법령해석 질의를 다듬음)

*(Claude 판단)* **근거 문서 ID의 단위**
- 법령은 **항** 단위로 붙인다(예: `근로기준법 제60조 제2항`). 항이 없는 조는 조 단위로 붙인다.
- 법령해석은 1건, FAQ는 1건이 한 단위다.
- 최저임금 고시는 조 · 항 구조가 아닐 수 있으므로 고시 1건을 한 단위로 본다.
- 이유: 조 단위는 너무 넓어서 "몇 항이 답인지"를 못 가리고, 호 단위는 검수 부담이 너무 크다.

*(Claude 판단)* **청크 경계가 실험마다 다를 때 맞은 것으로 보는 기준**
- 원문을 정제할 때 항마다 원문 내 위치(시작 · 끝 글자 위치)를 기록한다.
- 검색된 청크가 정답 항 범위의 **50% 이상을 덮으면** 그 근거를 찾은 것으로 본다. 글자 몇 개만 겹친 경우는 찾은 것으로 치지 않는다.
- 이유: 겹치기만 하면 맞다고 치면 긴 청크가 여러 항을 한꺼번에 덮어 recall이 부풀려진다.
- 실험마다 **평균 청크 길이**를 결과에 함께 남긴다. 청크 길이 차이로 생긴 이득인지 가려 보기 위해서다.
- 이렇게 하면 E0(고정 길이)과 E1(조 · 항 단위)을 같은 정답으로 비교할 수 있다.
- recall@k는 상위 k개 청크에서 찾은 정답 근거의 비율로 계산한다(5.1절).

### 4.3 만드는 방법

1. 법령해석 질의와 FAQ 질문에서 실제 질문을 가져와 다듬는다.
2. LLM으로 조문에서 질문 초안을 만든다.
3. **모든 문항을 사람이 검수한다.** 정답과 근거 문서를 원문과 맞춰 본다.
   - 검수는 사용자가 직접 한다. 1주차에 약 5~7시간이 든다.
   - 검수가 빠르도록 **검수 화면**을 만든다. 문항 · 정답 · 근거 원문을 나란히 보여주고 승인 · 수정 · 삭제를 누르게 한다. 결과는 파일로 저장한다.
   - 질문 초안을 만드는 시간이 검수 시간을 잡아먹지 않게, 초안은 먼저 한꺼번에 만들어 둔다.
4. 답 없음 · 개정 유형은 직접 만든다.

*(Claude 판단)* **평가에 쓴 원문은 말뭉치에서 뺀다**
- 평가 문항을 만드는 데 쓴 법령해석 · FAQ 원문은 검색 말뭉치에서 뺀다(별도 보관).
- 이유: 그대로 두면 질문과 거의 같은 문장이 말뭉치에 있어서 기준선부터 recall이 부풀려진다.
- 이렇게 하면 그 문항은 법령 조문이나 다른 FAQ에서 근거를 찾아야 한다. 정답 근거도 그 기준으로 붙인다.
- 문항 초안을 만들기 **전에** 어떤 원문을 평가용으로 뗄지 먼저 정하고, 그다음 말뭉치를 확정한다.

*(Claude 판단)* **답 없음 문항은 두 종류를 반씩 넣는다**
- 범위 밖 주제(산재 보상, 실업급여 등). 거절하기 쉽다.
- 범위 안 주제지만 말뭉치에 근거가 없는 질문. 예: 특정 회사 취업규칙에 달린 질문, 말뭉치에 없는 세부 사례. 거절하기 어렵다.
- 보고서에서는 둘의 거절률을 따로 적는다. 쉬운 쪽만 넣어서 수치가 좋아 보이는 것을 막기 위해서다.

### 4.4 개발 세트와 테스트 세트

- 대략 개발 60% / 테스트 40%로 나눈다. 유형 비율이 양쪽에서 비슷하게 유지되게 나눈다.
- **테스트 세트는 잠근다.** 설정 선택과 튜닝은 개발 세트로만 한다. 테스트 세트는 각 실험의 최종 설정을 확정한 뒤에 측정한다.
- 테스트 세트의 질문 · 정답은 파인튜닝 데이터와 프롬프트 예시에 쓰지 않는다. 파인튜닝 데이터를 만든 뒤, 테스트 질문과 거의 같은 문장이 섞이지 않았는지 자동으로 검사한다.

## 5. 지표

### 5.1 검색
- **recall@k** (k = 1, 5, 10): 문항의 정답 근거 중 상위 k개 청크에서 찾은 비율. 문항별로 계산해 평균 낸다.
- **all-hit@k:** 정답 근거를 상위 k개 안에서 **모두** 찾은 문항의 비율. 문서 간 연결 유형에서 특히 본다.
- **MRR:** 첫 정답 근거가 몇 번째에 나왔는가
- 찾았는지의 판정 기준은 4.2절을 따른다.
- 답 없음 문항은 정답 근거가 없으므로 검색 지표 계산에서 뺀다. 답 없음 문항은 5.2절의 거절률로만 평가한다.

### 5.2 답변
- **정답률:** 정답과 내용이 맞는가. 숫자가 있으면 숫자를 코드로 비교한다.
- **근거 충실도:** 답의 내용이 인용한 근거 문서에 실제로 있는가
- **환각 비율:** 근거 없는 내용을 단정한 답의 비율
- **답 없음 처리:** 답 없음 문항에서 거절했는가, 답이 있는 문항에서 잘못 거절하지 않았는가

### 5.3 자원 · 속도
- 질문당 지연 시간 (검색 / 생성 따로)
- 질문당 토큰 수, GPU 메모리 사용량

### 5.4 LLM 채점 검증
정답률 · 근거 충실도처럼 사람 판단이 필요한 지표는 **로컬 LLM**으로 채점한다. 다만 **LLM 채점을 믿을 수 있는지 먼저 확인한다.**
- 채점 모델은 그 답을 만든 모델과 **다른 모델**을 쓴다. 자기가 만든 답을 후하게 채점하는 것을 막기 위해서다. 예: qwen3가 만든 답은 exaone3.5가 채점한다.
- 숫자가 있는 정답은 LLM 채점보다 코드 비교를 우선한다.
- 개발 세트 일부(약 50개 답변)를 사용자가 직접 채점한다. 2주차에 약 2시간이 든다. 검수 화면을 채점에도 쓴다.
- LLM 채점과 얼마나 일치하는지 보고서에 적는다.
- 일치도가 낮으면 채점 프롬프트를 고치고, 그 과정도 기록한다.

## 6. 실험

모든 실험은 같은 평가 세트 · 같은 지표로 비교한다. 실험마다 설정 파일과 결과 파일을 남겨서 다시 돌릴 수 있게 한다.

| # | 실험 | 바꾸는 것 | 기대하는 효과 |
|---|---|---|---|
| E0 | 기준선 | 고정 길이 청킹 + 범용 다국어 임베딩 + 단순 프롬프트 | 출발점 수치 |
| E1 | 구조 청킹 | 조 · 항 단위로 자르고, 법령명 · 조 번호 · 제목을 청크에 붙임 | 조문 검색 정확도 |
| E2 | 하이브리드 검색 | 한국어 형태소 분석 기반 BM25 + 임베딩 검색 결합 | "제60조", "주휴" 같은 키워드 질문 |
| E3 | 리랭커 | 상위 후보를 cross-encoder로 다시 정렬 | 상위 1~5위 정밀도 |
| E4 | 질문 재작성 | 구어체 질문을 검색용 질의로 바꾸거나 여러 개로 나눔 | 조건 분기 · 문서 간 연결 |
| E5 | 임베딩 파인튜닝 | 이 분야 데이터로 임베딩 모델 학습 (7절) | 범용 모델 대비 recall |
| E6 | 생성 모델 비교 | 로컬 모델끼리 (exaone3.5 7.8b, qwen3 8b, 더 작은 모델 하나) | 품질 · 속도 · 메모리 균형 |
| E7 | 계산 도구 (여유 있으면) | 퇴직금 · 연차 계산을 코드 함수로 처리 | 계산 유형 정답률 |

- 실험은 앞 실험의 최선 설정 위에 하나씩 더하는 방식이 기본이다. 효과가 없는 단계는 빼고 다음으로 넘어가되, 결과는 보고서에 남긴다.
- 효과가 의외로 크거나 작으면 실패 사례를 몇 개 골라 원인을 분석한다. 이 분석이 보고서의 핵심 재료다.

## 7. 임베딩 파인튜닝 (E5)

- **목표:** 범용 한국어 · 다국어 임베딩 모델을 이 분야 데이터로 학습해서 검색 성능이 얼마나 오르는지 본다.
- **학습 데이터:** 말뭉치의 청크마다 로컬 LLM으로 "이 청크가 답이 되는 질문"을 만들어 (질문, 청크) 쌍을 만든다. 수천 개를 만드는 데 몇 시간이 걸릴 수 있으니 한 번 만들어 파일로 저장해 두고 다시 쓴다. 생성 결과는 형식과 품질을 자동으로 걸러 낸다(빈 질문, 청크 문장을 그대로 베낀 질문 등). 법령해석 질의 · 회신 쌍도 쓸 수 있다. 단, 평가 세트에 쓴 법령해석 건은 학습에서 뺀다.
- **누수 검사:** 학습 질문과 테스트 질문의 유사도를 계산해서 너무 비슷한 것은 학습에서 뺀다.
- **하드웨어:** RTX 4060 Laptop(VRAM 8GB). 큰 모델이 안 들어가면 작은 모델로 바꾸거나, 배치 크기 축소 · 혼합 정밀도 · 그래디언트 체크포인팅을 쓴다.
- **비교:** 같은 모델의 학습 전 vs 학습 후, 그리고 다른 범용 모델과 비교한다.
- 학습한 모델은 Hugging Face Hub에 올리는 것을 선택지로 둔다.

## 8. 답변 생성

- **시스템 코드의 모든 LLM 호출은 로컬 Ollama 모델로 한다.** 사용자가 API 예산을 0원으로 정했다. 해당하는 호출은 답변 생성, 채점, 질문 재작성, 파인튜닝 데이터 생성이다. 평가 문항 초안은 로컬 LLM으로 만들거나, 개발 도구인 Claude Code로 만든다(아래).
  - 쓸 모델: exaone3.5 7.8b, qwen3 8b. `D:\Ollama\models`에 이미 받아져 있다.
- **GPU 하나를 나눠 쓴다.** 8GB VRAM에는 LLM과 임베딩 학습이 동시에 들어가지 않는다. 생성 작업과 학습 작업은 순서대로 돌린다.
- *(Claude 판단)* 평가 문항 초안은 개발 중에 Claude Code가 함께 써도 된다. 공개 자료만 다루고 별도 API 비용이 들지 않는다. 다만 시스템 코드에는 Claude API 호출이 없다. 어떤 문항을 무엇으로 만들었는지는 4.2절의 "출처"에 남긴다.
- **답변 규칙**
  - 답의 각 주장에 근거 문서를 인용한다(법령명 · 조 번호 또는 FAQ 제목).
  - 검색된 문서에 근거가 없으면 "자료에서 찾을 수 없다"고 답한다.
  - 답에 "법률 자문이 아니며 기준일 시점의 법령 기준"이라는 안내를 붙인다.
- **검색된 문서는 데이터다.** 문서 안의 문장을 지시로 따르지 않게 프롬프트에서 문서와 지시를 구분한다.
- **LLM 결과는 형식이 틀릴 수 있다고 가정한다.** 인용 형식 · JSON 출력은 검증하고, 실패하면 정해진 횟수만 재시도한다.

## 13. 만드는 방식 (선택지와 결정)

### 13.1 검토한 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 실험 중심 (선택)** | 평가 도구와 실험 스크립트가 본체. 데모는 Gradio 하나 | AI 엔지니어 면접에서 묻는 "왜, 얼마나"에 시간을 다 씀 | 화면이 소박함 |
| B. 서비스 중심 | FastAPI + React 앱 안에 RAG | 완성된 제품처럼 보임 | 시간 절반이 화면에 들어감. FollowUp이 이미 보여준 역량과 겹침 |
| C. 프레임워크 비교 | LangChain · LlamaIndex 등으로 같은 문제 풀기 | 빨리 만들 수 있음 | "써 봤다"에 그치고 검색 원리를 보여주기 어려움 |

사용자는 **A**를 골랐다.

### 13.2 사용자가 정한 것
- 주제: 한국 근로 제도
- 폴더 · 저장소 이름: `labor-law-rag`
- 기간: 약 4주
- 방식: A (실험 중심)
- 법령 범위: 최저임금 고시, 고용보험법의 육아휴직 · 출산휴가 급여 조문, 퇴직급여법 시행령 추가(3.2절)
- API 예산: 0원. 모든 LLM 호출은 로컬
- 검수 · 채점: 사용자가 전부 직접

### 13.3 설계 단계에서 Claude가 정한 것 (2026-11-17 사용자 승인)
본문에 *(Claude 판단)*으로 표시한 곳과, 표시는 없지만 Claude가 제안한 결정이 여기에 해당한다. 사용자가 모두 승인했다.
- 데이터 출처 3가지(3.1절)
- 기준일 시행 조문만 넣고, 옛 기준 문서는 날짜와 함께 둠. 개정 유형의 정답 기준(3.3절)
- 평가 세트 약 150문항, 개발/테스트 6:4(4절)
- 정답 근거는 항 단위(고시는 1건 단위). 청크가 정답 항 범위의 50% 이상을 덮으면 찾은 것으로 봄(4.2절)
- recall@k는 정답 근거 중 찾은 비율. all-hit@k는 따로 봄. 답 없음 문항은 검색 지표에서 뺌(5.1절)
- 평가에 쓴 법령해석 · FAQ 원문은 말뭉치에서 뺌(4.3절)
- 답 없음 문항은 범위 밖 / 범위 안 근거 없음을 반씩(4.3절)
- 채점 모델은 답을 만든 모델과 다른 로컬 모델(5.4절)
- 평가 문항 초안은 개발 중 Claude Code가 함께 쓸 수 있음(8절)
- 데모는 Gradio, 로컬 전용(9절)
- 검색 단계는 프레임워크 없이 직접 구성

## 14. 만드는 사람에게 맡기는 것

다음은 설계에서 정하지 않는다. 구현 계획에서 정하고, 정한 이유를 판단 기록에 남긴다.

- 구체적인 임베딩 · 리랭커 모델 (한국어 지원, 8GB 안에서 돌아가는지 기준으로 고른다)
- 한국어 형태소 분석기 종류
- 벡터 저장 방식 (메모리 배열, FAISS 등. 말뭉치가 작으면 단순한 쪽)
- 고정 길이 청킹의 크기와 겹침 값
- 패키지 관리 도구와 폴더 구조
- 테스트 방식. 단, 외부 호출(LLM · API)은 가짜 구현으로 바꿔 끼울 수 있게 해서 테스트가 네트워크 없이 돌아가야 한다.
- 실험 결과 저장 형식 (설정 · 지표 · 실행 시각 · 코드 버전이 남으면 된다)

## 15. 작업 규칙

FollowUp Agent에서 쓰던 방식을 이어 간다.

- 문서와 커밋 메시지는 한국어로 쓴다. 커밋 메시지는 `영역: 내용` 형식이다.

- 구현이 계획과 달라지면 계획 문서 맨 아래 "계획 대비 변경 이력" 표에 남긴다.
- 의존성은 정확한 버전으로 고정한다.
